# N53 — actual Kotlin/Python WAV header comparison

**24 of 24 shared synthetic fixtures passed**, with exact agreement across 17
projected fields (408 field comparisons). Both implementations also met each
fixture's independently declared status and applicable duration checkpoints.
Kotlin ran as compiled JVM code; this was not a Python reimplementation of the
native parser or a comparison of expected-output files.

The final receipt, `docs/WAVE8_WAV_PARITY_RECEIPT.json`, records each supplied-byte
hash independently in Python and JVM, identical-input confirmation, unchanged
input bytes after both probes, effective-prefix hash, both projections, issue
codes, runtime versions and source/dependency fingerprints. All input-identity
and nonmutation checks passed. No production parser was changed by this task and
no discrepancy was observed within the tested shared argument domain.

## Reproduce without Gradle or downloads

From the repository root, with the existing cached toolchain:

```sh
python scripts/compare_wav_headers.py \
  --toolchain-root /tmp/ageds-clean-build-fw_7dz1b \
  --receipt docs/WAVE8_WAV_PARITY_RECEIPT.json
```

`--java` can select another existing JDK executable. The toolchain root must
contain the already cached Maven artifacts under
`gradle-user-home/caches/modules-2/files-2.1`; missing or ambiguous dependencies
fail explicitly without attempting a download. The runner uses Kotlin/compiler
plugin 2.4.20, kotlinx.serialization 1.11.0 and the cached JDK 21. Compiler outputs
are created in a temporary directory and removed after execution. A nonzero exit
status signals differing observations/checkpoints, changed sources during the
run, or execution failure. The receipt is written only after both implementations
run and the source fingerprints remain stable.

The reproducible files are outside Android/core build source sets:

- `scripts/wav_parity/fixtures.json` — 6,914-byte synthetic fixture manifest.
- `scripts/wav_parity/WavHeaderParityRunner.kt` — stdin JSON-lines JVM adapter.
- `scripts/compare_wav_headers.py` — bounded fixture generation, compilation,
  execution, exact projection comparison and receipt generation.

Fixtures contain explicit header hex plus optional bounded repeat/suffix recipes.
The Python harness generates each byte array once, sends those exact bytes as
base64 to Kotlin, and supplies the same bytes to Python. Kotlin does not separately
interpret the fixture recipe. The repeat mechanism covers 64 KiB boundaries
without storing a large repeated hex/audio body in the repository. Manifest size,
fixture count, repeat count and generated byte length have explicit harness bounds.

## Compared contract

The projection compares status, coverage, inspected-byte count, prefix limit,
effective EOF, provider size, RIFF declared extent, format code, channel count,
sample rate, byte rate, block alignment, sample width, declared data bytes,
declared duration, duration basis and the body-validation flag. Snake-case Python
and camel-case Kotlin names are explicitly mapped. JSON-decoded value types and
values must agree; fields are not normalized to make a mismatch disappear.
Literal issue message text is not compared. Issue codes are retained as evidence,
not used as the pass/fail oracle.

| Fixture family | Included cases |
|---|---|
| Supported profiles | Complete mono PCM16; stereo IEEE float32 with zero-length fmt18 extension; header-only PCM with unread declared data |
| Incomplete input | Empty prefix without EOF; eight-byte header at EOF; basic fmt fields outside prefix; missing declared body at EOF |
| Container/profile limits | RF64; non-WAVE RIFF form; too-small RIFF extent; compressed format; nonzero fmt extension |
| Conflicts and ambiguity | Provider-size disagreement; duplicate fmt; data-before-fmt; inconsistent byte rate; duplicate data; unaligned sample data |
| Chunk and numeric boundaries | Valid odd JUNK padding; missing required odd padding; unsigned 32-bit RIFF/data declarations |
| Bounded-prefix behavior | Large JUNK hides required headers; exact 65,536-byte prefix with unread body; 65,537-byte supplied prefix resets effective EOF |

The two valid full-file profiles and a valid header-only profile exercise concrete
shared behavior; malformed, unsupported and partial cases verify that agreement
is not limited to a happy path. Large RIFF/data extents are declarations in tiny
synthetic prefixes, not allocated multi-gigabyte media.

## Limits and deliberate differences

This compares pure prefix observations, **not SAF and POSIX scanner policies**.
It does not equate their source opening, no-follow behavior, provider metadata,
I/O budgets, full-hash coverage or cache/permission handling. No source scanner,
private corpus, real recording, decoder or ASR model ran here. `bodyValidated`
remains false; a matching duration is arithmetic on declarations, not acoustic
or complete-content verification.

Fixtures use the shared valid argument domain. Python deliberately rejects
negative/noninteger/boolean provider sizes and wrong argument types as API errors;
the native `Long?` interface has different type constraints and reports a negative
provider size as a malformed observation. This documented interface difference
is not silently counted as parity. Agreement on these 24 fixtures is not proof of
exhaustive RIFF/WAVE support or that both implementations cannot share an error.
Independent N51 semantic/adversarial checks remain separate evidence.
